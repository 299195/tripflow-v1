# TripFlow V2 需求与功能说明

## 1. 版本定位

TripFlow V2 是“可执行、可重规划的旅行助手”。用户可以生成行程、查看路线来源、在旅行过程中报告延误或地点不可用、比较调整方案、确认新版本并恢复历史版本。

V2 的多 Agent 用于意图理解、地点核验和方案审查；确定性规划器负责最终时间与硬约束校验。自进化指反馈驱动的离线策略评测和受门槛控制的策略发布。

## 2. 用户闭环

```text
生成攻略 → 选择地点 → 生成行程 → 查看路线
       → 报告延误/关闭/跳过 → 比较候选方案
       → 确认新版本 → 查看差异或恢复历史版本
```

## 3. V2 功能需求

### 3.1 真实路线与降级

- 行程生成优先调用高德步行路线。
- 每段路线保存交通方式、距离、预计时长、来源、获取时间和受控响应摘要。
- 路线来源明确区分 `amap`、缓存路线和估算路线。
- 高德失败时可使用带失败原因的直线估算；禁止把估算标为高德路线。
- 线路缓存带有效期，减少重复请求。

### 3.2 执行事件与重规划

- 支持延误、地点关闭和跳过地点。
- 重规划先生成预览，不立即修改当前行程。
- 每次预览最多返回 3 个候选方案。
- 候选方案展示受影响地点、时间变化和方案理由。
- 用户确认后创建不可变新版本。
- 当前版本发生变化时，旧预览不能确认，避免覆盖其他修改。
- 同一幂等键重复请求返回同一预览或已确认结果。

### 3.3 多 Agent

- 意图 Agent：提取目的地、用户偏好和硬约束。
- 地点核验 Agent：检查候选地点的名称、坐标和来源。
- 方案审查 Agent：检查规划结果是否存在冲突并生成审查结果。
- 每个节点记录角色、状态、策略版本、输入摘要、输出、错误、耗时和关联 ID。
- Agent 不直接写入行程；最终状态只能通过确定性服务和事务写入。

### 3.4 反馈与策略演进

- 用户可以接受、拒绝、跳过或报告方案。
- 反馈可以导出为 JSONL，并生成离线评测样本。
- 策略包含版本号、父版本、参数和生命周期状态。
- 基线与候选策略在同一数据集上比较硬约束违规、通过率、接受率、效用、延迟和成本。
- 硬约束退化或评测错误增加时，候选策略不能批准。
- 策略批准必须经过显式人工决策。

### 3.5 网页端

- 行程详情展示时间轴、地点状态、路线距离、时长、来源和预约提醒。
- 支持报告延误、地点关闭、跳过地点。
- 支持候选方案卡片比较和确认。
- 支持历史版本差异和恢复。
- 保留首页、探索和我的页面，并提供加载、错误、空结果和移动端状态。

## 4. V2 API

- `POST /api/v2/itineraries/{id}/replan/preview`
- `POST /api/v2/itineraries/{id}/replan/confirm`
- `POST /api/v2/itineraries/{id}/execution-events`
- `GET /api/v2/itineraries/{id}/versions/diff`
- `GET /api/v2/itineraries/{id}/agent-runs`
- `POST /api/v2/itineraries/{id}/feedback`

V1 API 保留，用于兼容已有页面和数据。V2 请求使用 Pydantic 模型校验，错误仍通过稳定的 HTTP 状态和错误信息返回。

## 5. V2 验收标准

- 规划主链路使用真实路线提供器；未配置地图 Key 时显式使用估算。
- 40 个本地确定性业务链路场景全部通过。
- 网页可以完成“生成、查看、报告事件、比较、确认、恢复”。
- 重规划确认失败时数据库不产生部分修改。
- 可查询一次重规划中的多个 Agent 运行记录。
- 离线评测可以批准改进策略，也可以拒绝硬约束退化策略。
- 所有真实外部 API、fixture 和离线结果分开报告。

## 6. 已知限制

- 当前路线首个真实模式是步行；驾车、公交和骑行保留扩展空间。
- 当前 Agent 节点提供确定性 fallback；模型调用能力仍受 Qwen 配置和网络影响。
- V2 的自进化是离线策略演进，不包含在线自动改代码、自动训练或自动发布。
- V1 仍是单用户本地身份和 SQLite 部署，未提供生产级多租户认证。
